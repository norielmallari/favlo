# Gemma 4 26B-A4B

As-built note for the `gemma4-26b-a4b` pipeline. Pack and the first chat are [SETUP.md](SETUP.md). The process contract is [../../ARCHITECTURE.md](../../ARCHITECTURE.md). This directory wins for this pipeline's records and kernels. Another pipeline does not edit it.

`handle_responses` is a `LanguagePipeline`. The completion, the sampler, and the stream stay in this package and read a Responses body. The listener translates a Chat Completions body into that request and translates the Response back. Clients reach this pipeline through `favlo serve`. `GET /v1/models` lists it once a record is registered, and the `model` field on `POST /v1/responses` loads it. `plan`, `quantize`, `kernels`, and `complete` require `favlo --gemma4-26b-a4b`. That flag loads `pipelines/metal41/gemma4-26b-a4b.py`, which loads `gemma4_26b_a4b`.

The official checkpoint is [google/gemma-4-26B-A4B-it](https://huggingface.co/google/gemma-4-26B-A4B-it). Those weights are under the [Apache License, Version 2.0](https://ai.google.dev/gemma/docs/gemma_4_license). `quantize` does not download. With no `--src` it reads `models/gemma-4-26B-A4B-it`. Device spans come from `device_buffer`. `open_runtime` takes `owner` and every span from that opening uses it. `close` sweeps that string. A command that omits `owner` mints one from this runtime's id. The opening reads `budget()` from the serve ledger. `--max-memory` is that ledger's cap. It keeps every expert layer that fits after `resident.bin`, the scratch, and the key/value cache. Each prefill chunk reads the ledger again. A larger answer admits more expert layers. A smaller answer leaves the resident layers in place. The cache starts at 256 tokens and doubles. Growth releases layer files until the new cache and at least one layer file fit. A layer that is not resident is read into the oldest slot before that layer runs. The opening refuses when one layer file does not fit. A request logs prompt tokens, a cache hit or miss, and the prefill and decode counts while those phases run. The prefill count stays short of the prompt until the chunk's command buffer has finished. The embedding and the dense projections are fp8. Decode reads those in `embed_fp8` and `gemv_fp8`, and the routed experts in `gemv_fp4_at` and `gemv_fp8_at`. Prefill restores each dense projection into an int8 stage for the chunk tile. Prefill reads a chunk of 1024 tokens.

## Kernels

`kernels` compiles this package's shader library and dispatches one fp8 `matmul2d`, one fp4 `matmul2d`, one Metal half `matmul2d`, and one int8 prefill tile. The fp8 and fp4 left operand is Metal half, the destination is float32, and a quantized right-hand tensor is dequantized inside the op. The int8 path restores a packed fp8 matrix into a per-row int8 stage, quantizes a float or half activation, multiplies with `prefill_i8_n64`, and scales the int32 product back to float. The fp8 and fp4 checks compare that product with the packed restore. The int8 check compares restore codes, activation codes, and the scaled tile. The prefix check copies filled Metal half tokens and compares those bytes with the host half pack. A missing kernel stays missing.

## Record

`plan` prints packed sizes from the checkpoint shapes. `quantize` streams a local bfloat16 checkout into `models/gemma-4-26B-A4B-it-fp8-e20`. Resident matrices, including the token embedding, are fp8 E4M3 with one E8M0 scale per 32 values. Routed experts are quantized from that bfloat16 checkout. Each expert is scored by the fp4 relative RMS of its gate-up and of its down projection, and the score is the larger of the two. The highest 20% are stored as fp8 and the rest as fp4. Gate-up and down move together. The fp4 encoder keeps the exponent with the smallest squared error. The fp8 encoder uses the block peak. `expert_error.json` records the percentage, the pool, the count, the promoted pairs, and every plane score before the images are written. `experts/widths.bin` is one byte per expert, 8 for a promoted expert and 4 for the rest. A finished directory whose manifest says the resident plane is `fp8`, the expert plane is `fp8-e20`, and the promotion is 20 returns. An older complete record is packed again. An unfinished `fp8-e20` directory resumes from `quantize_progress.json`. fp8 K is padded to a multiple of 128 and fp4 K to a multiple of 256. A matrix whose row count is not a multiple of 32 gains zero rows so the fp8 tile fits. The 128 experts of a layer are packed together, and a resident matrix of 8192 or more rows is packed in row spans of 8192. Each worker uses one BLAS thread.

`plan` reports resident matrices of 3,032,502,528 bytes, scratch of 0 bytes, Metal half vectors of 70,474,908 bytes, and expert images of 14,853,341,184 bytes. Routed experts stay in `experts/<layer>.bin`. A layer file is 128 expert images in expert-index order. An image is that expert's gate-up data, its E8M0 scales, the down data, and its scales. Opening the record reads `widths.bin`, places each image on a 128-byte boundary, and checks the file length. It shows that read while it runs. A token indexes eight experts in the layer file. Resident matrices and the Metal half vectors are `resident.bin` with `resident.json`. The token embedding, the attention projections, the shared MLP, and the vision linears are fp8. The router, the norms, `router.scale`, `per_expert_scale`, `layer_scalar`, and the vision vectors stay Metal half. The drafter is not in this record. The vision tower stays in that file and is loaded on the first image. A text-only open does not read it. Soft rows for a PNG are also stored under `~/.favlo/vision-cache/gemma4-26b-a4b/`, so a later serve process that sees the same bytes logs `vision cache` and does not rerun the tower. The runtime keeps the resident fp8 bytes. Decode reads a projection in `gemv_fp8` and the embedding in `embed_fp8`. The eight routed experts of a token launch from the ids the router wrote on device, one `gemv_fp4_at` and one `gemv_fp8_at` per projection, and the token does not read those ids back. A prefill chunk is 1024 tokens and submits every ten layers, so the prefill count advances while the device runs. On `fp8_e4m3`, prefill scores every key head of a tile with `matmul_half_64_batch` and decode scores them with `matmul_half_batch`. On `half`, local attention is `attend_span4`, four queries sharing each key load, and global attention is `attend_span`. Expert prefill groups the routed rows on device. The slot tables and the matmul grid stay there, so the host does not read the ids. Expert prefill reads the stored image. Occupied slots are padded to 64. An fp4 expert uses `matmul_fp4_64_at` and an fp8 expert uses `matmul_fp8_64_at`. Decode reads the same bytes in `gemv_fp4_at` and `gemv_fp8_at`. The down projection pads K from 704 to 768. A dense prefill batch restores the large attention projections into an int8 stage and multiplies with `prefill_i8_n64` when the chunk is at least 256 tokens. Local key and value, the shared MLP, and shorter chunks stay on `matmul_fp8`. Decode stays `gemv_fp8` on the packed bytes. The atlas is not expanded. The router stays Metal half and uses `matmul2d`. Bandwidth and kernel ceilings are in [ceilings.md](ceilings.md).

## Forward

The text decoder has 30 layers, hidden size 2816, and a tied embedding of 262,144 rows. Layers 5, 11, 17, 23, and 29 are global. A global layer stores keys and values. The value is an RMSNorm, with no scale, of the key projection, and it is not rotated. Local values are that same norm of the value projection. Attention scores are the raw dot. The other 25 layers are local, with a sliding window of 1024. Local heads are 16 query heads of dimension 256 and 8 key and value heads. Global heads are 16 query heads of dimension 512 and 2 key heads. Full rotary embeddings use θ = 10,000 on every local pair. Global layers use proportional rotary embeddings, θ = 1,000,000, on the first quarter of the pairs (Barbero et al.). The remaining pairs are the identity. The rotation is the first half against the second half. RMSNorm uses the stored scale as the multiplier, with ε = 10⁻⁶. Query and key norms are one vector of the head dimension, applied to each head. The shared MLP and each routed expert use the tanh approximation of GELU. The router is a Metal half product. Its input is RMSNorm with the stored `router.scale` multiplied by `1/sqrt(hidden)`. A device kernel keeps eight of 128 experts, renormalizes them, and multiplies by `per_expert_scale`. The token embedding row is read as fp8 on device and multiplied by `sqrt(hidden)`. Final logits use the tied embedding, with no extra scale, and the soft cap 30, `30 · tanh(logits / 30)`. Temperature, top-k, top-p, and the presence penalty run on device. The CPU reads eight expert ids per layer and the one sampled token. Dispatches in one layer share a command buffer until that read. The next buffer waits on a fence. Query and key norms are one launch per tensor. On `half`, decode attention is `attend_decode`. One simd walks a short cache. At 256 keys the walk splits across four simdgroups, and at 1024 keys across eight. They merge one online softmax. Prefill local attention is `attend_span4`. Prefill global attention is `attend_span`. On `fp8_e4m3` those walks are the matmul dispatches in the cache section.

Attention and both feed-forward branches add at scale one. The dense MLP uses `pre_feedforward_layernorm` and `post_feedforward_layernorm_1`. Routed experts use `pre_feedforward_layernorm_2` and `post_feedforward_layernorm_2`. `post_feedforward_layernorm` normalizes the sum of those branches. `layer_scalar` then multiplies the hidden state. A generation that collects 6 carrots is what accepts the block.

An image request loads the 550M vision tower from those packed fp8 rows. The resize is Algorithm 1: pooled patch 48, at most 280 soft tokens, bicubic, then rescale by 1/255. Each patch is 16×16×3 in row order. The encoder has 27 layers of width 1152 and 16 heads of dimension 72. Attention is non-causal and the score is the raw dot. Values use an unscaled RMSNorm. Axial 2D-RoPE uses θ = 100: the first half of the head rotates with the column (x) and the second half with the row (y), each half pairing its first 18 values with its second 18. Patch pixels are scaled to `[-1, 1]`. The absolute table adds axis 0 at the column (x) and axis 1 at the row (y) after the patch embed. Each block matches the text attention residual without a layer scalar: RMSNorm, attention, post-attention RMSNorm, residual, then the tanh-GELU MLP with its pre and post RMSNorms. A 3×3 average pools the encoder, the pooled rows are scaled by `sqrt(1152)`, then `(row - std_bias) * std_scale` standardizes them in float. An unscaled RMSNorm and `embedding_projection` map soft tokens into the text width. Each template `<|image|>` expands to begin-of-image, one placeholder per soft token, and end-of-image; only the placeholders receive soft embeddings. Those linears are the fp8 rows already in the record, so a second quantize is not required. The expanded length is `prompt_tokens`. An image prompt is stored in the prefix file in the live plane, the same way a text prompt is. The tower encodes a PNG once. A later process with the same bytes loads the soft rows from `~/.favlo/vision-cache/gemma4-26b-a4b/`.

The served window is 131,072 tokens. The checkpoint position limit is 262,144. The live key and value cache defaults to `fp8_e4m3`. The registry field is `kv_cache` with value `half` or `fp8_e4m3`. An omitted cache uses `fp8_e4m3`. `fp8_e4m3` stores one E4M3 record per head per token (`dim` codes plus `dim/32` E8M0 scales) in token-major order for keys and values. Local and global attend dequantize every key head of a tile to half. Prefill scores that plane with ``matmul_half_64_batch``. Decode scores it with ``matmul_half_batch``. The score is the raw dot. The value mix is the same product. A prefill chunk commits the command buffer every 1024 keys so the window server can run. A decode step keeps those dispatches in the layer buffer. `half` stores Metal halves in the same token-major layout. The cache starts at 256 tokens and doubles. Growth waits for the open prefill chunk, then copies the live tokens into the new buffer. The prefix file stores local keys and values, and global keys and values, in the live cache layout for the loaded plane. Capture copies the filled tokens from the device buffers, and install writes those bytes back. An exact-length file is not sampled. The next token is still stepped. A prompt that extends the live tokens continues. Any other prompt writes the live sequence and loads the longest stored strict prefix.
